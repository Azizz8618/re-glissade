# Ранбук: подъём моста DKS между БЭСМ-6 и «Электроника-60»

Дата: 19 ноября 2026 года. Ранбук составлен по исходникам и конфигурациям
репозитория `/home/azizz/Yandex.Disk/simh` (ветка с ДКС) и по отчёту
приёмки `dks-pdp11-bundle/ОТЧЁТ_О_ТЕСТАХ.md`. Ни одно утверждение ниже не
является предположением: все адреса, опкоды, имена регистров и строки трассы
взяты из файлов, перечисленных в разделе 8.

Мост уже работает в эталонной связке: это готовый механизм, а не объект
разработки. Задача ранбука — воспроизвести его на стенде и быстро понять,
где именно он не поднялся.

## 1. Что считается поднятым мостом

Критерии готовности (все должны выполняться одновременно):

1. Два процесса SIMH запущены: `besm6` с `SET DKS REMOTE=localhost:4140`
   и `pdp11` с `SET DKS BRIDGE=4140`.
2. `SHOW DKS` на БЭСМ-6 показывает `remote=localhost:4140 chans=2 (up)`;
   счётчики `BREAD`, `BWRITE`, `BATTN` растут, `BERR = 0`.
3. Чтение ячейки 0 Э-60 через мост возвращает `002000` (один концентратор
   на канале 2) или `006000` (два: каналы 2 и 3).
4. В трассе есть пары строк `032: [2]00000 -> 002000` на БЭСМ-6 и
   `bridge: READ [2]00000 -> 002000` на Э-60; записи
   `0132: [2]0154 <- ...` и `bridge: WRITE [2]0154 <- ...`.
5. При подключении telnet-терминала на 4300 Э-60 выставляет системный
   запрос, и на БЭСМ-6 появляется `bridge: <- ATTN (ПРП 6) + ПРП12`.
6. Приёмка: 63+ юнит-тестов, 0 FAIL; с подлинной ОС Диспак 9/9 + 11/11 =
   20/20.

## 2. Сборка

Команды проверены по `makefile` (цели `pdp11` в строке 2755 и `besm6` в
строке 3102):

```sh
cd /home/azizz/Yandex.Disk/simh
make besm6 ANSWER=N
make pdp11 ANSWER=N
ls -l BIN/besm6 BIN/pdp11
```

Пояснения по флагам:

- `ANSWER=N` — подавление интерактивного запроса о автоматической
  установке необязательных системных пакетов (`makefile`, обработка
  переменной `ANSWER`). Это единственный «флаг», который нужно передать;
  никаких `DKS=...` при сборке нет — устройство DKS входит в состав
  исходников `BESM6` и `PDP11` обычным образом.
- Цель `besm6` собирается с `NOCPP=1` (записано в правиле makefile).
  Сборка требует SDL2 и SDL2_ttf: в `makefile` для `besm6` включается
  `BESM6_BUILD = true`. Если заголовки отсутствуют, установите `ANSWER=Y` и
  разрешите менеджеру пакетов доустановить их, либо установите
  `libsdl2-dev` и `libsdl2-ttf-dev` вручную.
- Цель `pdp11` на обычном хосте собирает только `BIN/pdp11`;
  `pidp11-frontpanel` подключается лишь на Raspberry Pi.
- Сборка инкрементальная: после изменения `pdp11_dks.c` достаточно
  `make pdp11 ANSWER=N`, после `besm6_dks.c` — `make besm6 ANSWER=N`.

Константы протокола объявлены в `PDP11/pdp11_dks.h` и продублированы в
`BESM6/besm6_dks.c`. Это два отдельных файла, и при любом изменении
протокола их нужно править синхронно (см. раздел 7).

## 3. Подготовка каталога и порядок запуска

INI-файлы используют относительные пути к дискам и журналам, поэтому удобнее
запускать симуляторы из отдельного рабочего каталога. Он должен содержать
четыре файла (это перечислено в заголовке `dks_os_R.ini`):

- `boot_dispak.b6` — загрузчик;
- `2053` — системный МД;
- `2048` — рабочий МД;
- `2095` — МД архива (без него ОС циклится на приказе «УСТ.МД АРХИВА»).

Файлы `2052.bin`, `drum1x.bin`, `drum2x.bin`, `output_R.txt` создаются
самим симулятором при запуске. Журналы пишутся в подкаталог `logs/`.

```sh
mkdir -p /tmp/dks-run/logs
cd /tmp/dks-run
cp /home/azizz/Yandex.Disk/simh/BESM6/OSZAGR/dks_os_R.ini \
   /home/azizz/Yandex.Disk/simh/BESM6/OSZAGR/e60_R0.ini \
   /home/azizz/Yandex.Disk/simh/BESM6/OSZAGR/e60_R1.ini .
cp /home/azizz/Yandex.Disk/simh/BESM6/boot_dispak.b6 .
cp /home/azizz/Yandex.Disk/simh/BESM6/MD/2053 \
   /home/azizz/Yandex.Disk/simh/BESM6/MD/2048 \
   /home/azizz/Yandex.Disk/simh/BESM6/MD/2095 .
```

Порядок запуска не критичен: клиент на БЭСМ-6 повторяет подключение по
таймеру. Рекомендуемый порядок — сначала сервер (Э-60), затем клиент
(БЭСМ-6). Каждый симулятор запускается в своём окне терминала; все три
команды выполняются из `/tmp/dks-run`.

Терминал 1 — первый концентратор, канал КРК 2, мост 4140, telnet 4300:

```sh
/home/azizz/Yandex.Disk/simh/BIN/pdp11 e60_R0.ini
```

Терминал 2 — второй концентратор, канал КРК 3, мост 4141, telnet 4301
(пропустите, если второй Э-60 не нужен):

```sh
/home/azizz/Yandex.Disk/simh/BIN/pdp11 e60_R1.ini
```

Терминал 3 — БЭСМ-6 с Диспаком, клиент моста:

```sh
/home/azizz/Yandex.Disk/simh/BIN/besm6 dks_os_R.ini
```

Если запущен только один концентратор, уберите `set dks chans=2` из
`dks_os_R.ini`, иначе второй клиент будет постоянно пытаться
подключиться к порту 4141, а ячейка 0 покажет `002000` вместо `006000`.

Терминал Диспака за Э-60: `telnet localhost 4300` (или 4301). Пульт
оператора — окно симулятора БЭСМ-6, где выполнена команда
`attach tty1 console`: там проходит диалог загрузки «ДАТА/ВРЕМЯ».
Telnet-клиенты мукса на порту 4198 не отнимают пульт, пока это
подключение активно.

SHMEM-вариант (без сети, один хост) поднимается парой:

```sh

/home/azizz/Yandex.Disk/simh/BIN/besm6 dks_os_shm.ini  # SET DKS SHMEM=/dks
```

Для второго канала нужна вторая Э-60 с `SET DKS SHMEM=/dks1` и
`SET DKS CHAN=3`; на БЭСМ-6 остаётся `CHANS=2`.

## 4. Проверка, что мост поднят

### 4.1 Команды SCP

На стороне БЭСМ-6 в окне симулятора (Ctrl-E останавливает CPU и выдаёт
приглашение `sim>`):

```text
sim> SHOW DKS
sim> EXAMINE DKS CHAN
sim> EXAMINE DKS CHANS
sim> EXAMINE DKS BREAD
sim> EXAMINE DKS BWRITE
sim> EXAMINE DKS BATTN
sim> EXAMINE DKS BBULK
sim> EXAMINE DKS BERR
sim> EXAMINE DKS MEM[96]
```

Имена регистров взяты из массива `dks_reg[]` в `besm6_dks.c`: `CHAN`
(текущий канал КРК), `CHANS`, `MEM` (ОЗУ Э-60, 32768 слов), `BREAD`,
`BWRITE`, `BATTN`, `BBULK`, `BERR` — счётчики кадров моста.
`EXAMINE DKS MEM[96]` — это адрес `0140` (АБУФS); индекс указывается в
десятичном виде.

На стороне Э-60 доступны:

```text
sim> SHOW DKS
sim> SHOW DKS CONNECTIONS
sim> SHOW DKS STATISTICS
sim> EXAMINE DKS BREAD
sim> EXAMINE DKS BWRITE
sim> EXAMINE DKS BATTN
sim> EXAMINE DKS BPING
sim> EXAMINE DKS BBAD
sim> EXAMINE DKS BBULK
sim> EXAMINE DKS MEM[96]
sim> EXAMINE DKS KCTL
sim> EXAMINE DKS CSR
```

Регистры `BREAD/BWRITE/BATTN/BPING/BBAD/BBULK` объявлены в `dks_reg[]`
файла `pdp11_dks.c`. `BBAD` должен быть нулевым; рост `BREAD/BWRITE`
доказывает, что кадры доходят до Э-60. Пример сообщений отладочного
вывода, который нужно искать в журналах:

```text
bridge: client 127.0.0.1 connected     ; Э-60 приняла клиента
bridge up                             ; БЭСМ-6: подключение завершено
032: [2]00000 -> 002000               ; чтение ячейки 0 через КАДОПАМ
bridge: READ [2]00000 -> 002000       ; тот же кадр на Э-60
0132: [2]77777 <- 000400              ; звонок БЭСМ-6
doorbell from БЭСМ-6                  ; реакция Э-60 на звонок
bridge: <- ATTN (ПРП 6)+ ПРП12        ; системный запрос от Э-60
connect reply term 17 result 0        ; ответ АБФОСH
```

### 4.2 Debug-флаги и логи

Флаги задаются разделёнными точкой с запятой именами в `SET DKS DEBUG=...`.

На БЭСМ-6 (`besm6_dks.c`, таблица `dks_deb`) доступны:

| Флаг | Что пишет |
|------|-----------|
| `KADOPAM` | каждое обращение 032/0132 |
| `RING` | слоты колец, системные запросы, записи областей |
| `IRQ` | поднятые ПРП (ПРП6, ПРП12 и другие) |
| `BRIDGE` | кадры моста, ATTN, ошибки кадров |

На Э-60 (`pdp11_dks.c`) доступны `KADOPAM`, `RING`, `IRQ`, `DATA`
(символы линий), `PROTO` (состояния линий), `BRIDGE` (кадры).

В эталонных INI включены:

```ini
set dks debug=kadopam;ring;irq;bridge        ; БЭСМ-6
set dks debug=bridge;kadopam;ring;irq        ; Э-60
set debug -F LOG
```

Ключевые правила журналирования (проверены приёмкой):

- `SET DEBUG -F LOG` направляет трассу в **журнал консоли**, а не в
  отдельный файл. Отдельный `SET DEBUG FILE` — это обычный `FILE*`,
  который SIMH не сбрасывает на диск при каждом останове, поэтому во
  время работы в нём будет «хвост».
- `-F` отключает дедупликацию («same as above»), благодаря чему счётчики
  вхождений в трассе остаются осмысленными.
- `DE INT-FLUSH FLUSH_INTERVAL 1` в начале каждого INI обеспечивает
  сброс журнала консоли раз в секунду.
- Журналы эталонной связки: `logs/log_R.txt` (БЭСМ-6), `logs/e60_R0.mux`
  и `logs/e60_R1.mux` (Э-60).
- SIMH читает консоль с клавиатуры только когда `isatty(0)`. Если
  запускать симулятор на пайпе, Ctrl-E не работает, а команды копятся
  в очереди. Для сценариев используйте pty (`pty.fork` в тестах).

### 4.3 Трассировка кадров

Кадр виден одновременно в двух журналах: `032:`/`0132:` на БЭСМ-6 и
`bridge: READ`/`bridge: WRITE` на Э-60. По ним можно сличить не только
факт обмена, но и адрес, канал и значение. Полезная пара для проверки:

```sh
grep -E '032: \[2\]00000|bridge: READ \[2\]00000' logs/log_R.txt
grep -E 'bridge: READ|doorbell from|ATTN' logs/e60_R0.mux
```

Счётчики `BREAD`/`BWRITE`/`BATTN`, показанные `EXAMINE DKS`, позволяют
проверить мост без чтения журнала: попросите терминал на 4300 и
сравните прирост `BREAD` и `BATTN`.

## 5. Формат кадра и системные ячейки Э-60

### 5.1 Кадр моста

Протокол определён в комментариях `besm6_dks.c` (строки 98–130) и
`pdp11_dks.c` (строки 113–131). Все числа — байты; адреса и значения
передаются старшим байтом вперёд.

```text
запрос   D6 op chan addr_hi addr_lo val_hi val_lo 00
ответ    D7 (op | 0200) chan addr_hi addr_lo val_hi val_lo 00
```

- `D6` — маркер запроса (БЭСМ-6 → Э-60), `D7` — маркер ответа.
- `op | 0200` — в исходниках записано `op | 0x80`, то есть тот же бит
  0200 восьмеричный.
- `chan` — номер канала КРК, маскируется в 0–3.
- `addr_hi addr_lo` — 16-разрядный адрес слова ОЗУ Э-60 (0–077777).
- `val_hi val_lo` — 16-разрядное слово для записи; в ответе READ лежит
  считанное слово.

Опкоды:

| Код | Имя | Смысл |
|-----|-----|-------|
| 01 | READ | кадр для команды 032 БЭСМ-6 |
| 02 | WRITE | кадр для команды 0132 БЭСМ-6 |
| 03 | ATTN | Э-60 → БЭСМ-6: прерывание (ПРП канала + ПРП12) |
| 04 | PING | проверка живости моста |
| 05 | BULK_READ | запрос 8 байт; ответ 8 + 2·cnt |
| 06 | BULK_WRITE | запрос 8 + 2·cnt; ответ 8 |

BULK-кадры появились на этапе C. Счётчик `cnt` лежит в байте 5 запроса
(на месте `val_hi`), данные начинаются с байта 8 парами `старший,
младший`. Диапазон данных — адреса 1..077776: ячейка 0 (выбор канала) и
звонок 077777 сохраняют одиночные кадры со своими побочными эффектами.
БЭСМ-6 склеивает последовательные возрастающие записи 0132 в один
BULK_WRITE до 64 слов; любое другое действие сбрасывает буфер склейки.

### 5.2 Команды 032 и 0132

`besm6_cpu.c:1365–1371` диспетчеризует команды в `dks_read()` и
`dks_write()`:

- **032** читает 16-разрядное слово в разряды 25–40 аккумулятора.
  Чтение ячейки 0 возвращает статус канала: бит `9+k` означает,
  что канал `k` присутствует. Канал 2 даёт `0400 << 2 = 002000`,
  каналы 2 и 3 вместе — `006000`.
- **0132** записывает младшие 16 разрядов аккумулятора. Запись в ячейку
  0 выбирает канал КРК (это решение принимается локально, на БЭСМ-6).
  Запись `0400` в звонок `077777` будит Э-60.
- Ячейка 2 (номнпр) читается как 0.

### 5.3 Системные ячейки ОЗУ Э-60

Адреса словесные, восьмеричные. Таблица svyaz7.be, совпадает в
`besm6_dks.c` и `pdp11_dks.h`.

| Адрес | Имя | Назначение |
|-------|-----|------------|
| 0 | выбор канала / статус | запись выбирает КРК-канал, чтение отдаёт `0400 << k` |
| 00002 | номнпр | 0, чтобы рспец не вмешивался |
| 00140 | АБУФS | кольцо Э-60 → БЭСМ-6: +0 источник, +1 приёмник, +2..+5 слоты |
| 00146 | АБУФH | кольцо БЭСМ-6 → Э-60, та же структура |
| 00154 | АБФОСS | системный запрос: +0 код (1 подключить, 3 отключить), +1 линия, +2 область |
| 00157 | АБФОСH | системный ответ: +0 = 2, +1 номер терминала, +2 результат (0 ОК) |
| 077777 | адркс, звонок | запись 0400 будит Э-60; прочие биты — диагностический след |

Кольца имеют 4 слота (маска 3). Абонент 48 — системные запросы и ответы,
абоненты 1–24 — номера линий. Область терминала `n` расположена по адресу
`01000 + n × 01400`; смещения +0/+1 — флаги ввода/вывода (`020000`), +2 —
команда от Э-60 (4 ввод готов, 5 вывод сделан), +3 — адрес входного
буфера, +5 — команда от ОС, +6/+7 — адрес и длина выходного массива.

ПРП назначаются так (макрос `PRP_DKS_CHAN(n) = 0200 >> n`):
канал 0 → ПРП8, канал 1 → ПРП7, канал 2 → ПРП6, канал 3 → ПРП5.
Системный запрос дополнительно поднимает `PRP_DKS_ATTN` (ПРП12): этого
ждёт СВЯЗЬ7/Диспак, чтобы запустить «нтерм7».

## 6. Мини-тест одного кадра 032/0132

### 6.1 Вариант А: сырой кадр против моста (сторона Э-60)

Этот тест проверяет сам формат кадра и реакции устройства. Он работает,
когда к мосту не подключена БЭСМ-6: сервер принимает **одного** клиента и
новое подключение вытесняет предыдущее (`dks_bridge_poll()`), поэтому
перед тестом остановите БЭСМ-6 или выполните на ней `SET DKS LOCAL`.

Сохраните как `dks_one_frame.py` и запустите `python3 dks_one_frame.py`:

```python
import socket

HOST, PORT = "127.0.0.1", 4140

def xact(sock, op, chan=2, addr=0, val=0, payload=b""):
    req = bytes([0xD6, op, chan, addr >> 8, addr & 0xFF,
                 val >> 8, val & 0xFF, 0]) + payload
    sock.sendall(req)
    need = 8
    if op == 5:                      # BULK_READ: в ответе cnt слов
        need = 8
    data = b""
    while len(data) < need:
        data += sock.recv(need - len(data))
    if op == 5:
        need = 8 + 2 * data[5]
        while len(data) < need:
            data += sock.recv(need - len(data))
    return data

s = socket.create_connection((HOST, PORT), timeout=5)
s.settimeout(5)

r = xact(s, 4)                       # PING
assert r[0] == 0xD7 and r[1] == 0x84, r.hex()

r = xact(s, 1, addr=0)               # 032: ячейка 0 -> статус канала
status = (r[5] << 8) | r[6]
assert status == 0o002000, oct(status)

r = xact(s, 2, addr=0o50000, val=0o123456)  # 0132: нейтральное слово ОЗУ
assert r[1] == 0x82, r.hex()

r = xact(s, 1, addr=0o50000)                # 032: прочитать обратно
assert ((r[5] << 8) | r[6]) == 0o123456, r.hex()

xact(s, 2, addr=0o177777, val=0o400)       # звонок БЭСМ-6 -> Э-60
print("кадры PING/READ/WRITE/звонок прошли")
s.close()
```

Ожидаемые строки в `logs/e60_R0.mux` при включённом `BRIDGE`:

```text
bridge: client 127.0.0.1 connected
bridge: PING
bridge: READ [2]00000 -> 002000
bridge: WRITE [2]50000 <- 123456
bridge: READ [2]50000 -> 123456
bridge: WRITE [2]77777 <- 000400
doorbell from БЭСМ-6
```

### 6.2 Вариант Б: сквозной тест двух процессов (обе машины)

Готовый приёмочный тест поднимает оба симулятора и проверяет обмен
полным протоколом:

```sh
cd /home/azizz/Yandex.Disk/simh
PDP11/tests/dks_b2_test.sh BIN/pdp11 BIN/besm6 4140
```

Он выполняет девять проверок B2.1–B2.9: принятие клиента, `bridge up`,
`032: [2]00000 -> 002000`, приветствие терминала, двойное эхо HELLO,
достижение ответа АБФОСH до Э-60, ПРП6 по ATTN-кадру, доставка звонка
и прохождение выходного массива через ОС-заглушку. В конце тест пишет
`passed: 9, failed: 0`.

Для проверки именно «одного кадра» в сквозном режиме удобно взять
счётчики: запомнить `EXAMINE DKS BREAD` на Э-60, отправить один символ
в telnet 4300 и убедиться, что `BREAD` увеличился ровно на число
кадров, ожидаемых для системного запроса, а в журнале БЭСМ-6 появилась
соответствующая строка `032:`/`0132:`.

Полный набор приёмки (63+ проверок): `PDP11/tests/dks_run_tests.sh`,
затем `dks_b1_test.sh`, `dks_b2_test.sh`, `dks_c_test.sh` и

## 7. Частые ошибки и причины

| Симптом | Причина | Что делать |
|---------|---------|------------|
| `address already in use` при старте Э-60 | Порт 4140 (или 4300) занят предыдущим процессом или вторым Э-60 | `ss -ltnp | grep -E '4140\|4141\|4300\|4301'`, завершить старый процесс; не запускать `e60_R0.ini` дважды |
| Клиент на БЭСМ-6 не подключается, в трассе `bridge: connection refused` | Э-60 не запущена либо слушает другой порт | Поднять `pdp11 e60_R0.ini` первым; сверить `set dks bridge=4140` и `set dks remote=localhost:4140` |
| Ячейка 0 равна `002000` вместо `006000` | Второй клиент не подключился: нет второго Э-60 или не задан `CHANS=2` | Запустить `e60_R1.ini` (порт 4141, `chan=3`) и проверить `set dks chans=2` в `dks_os_R.ini` |
| Неверный SCN / номер канала КРК | В DKS-конфигурациях отдельного параметра `SCN` нет: под ним понимают номер канала КРК и базовый порт моста. БЭСМ-6: `CHANS=2` открывает каналы 2 и 3 на портах `p` и `p+1`; Э-60: `SET DKS CHAN=k` (по умолчанию 2). Рассинхрон даёт кадры с «чужим» каналом, не те ПРП и молчание ОС | Сверить `DKS_CHAN 2` в обоих исходниках, `set dks chan=2` (или `=3` для R1) и номера портов. Канал 2 — ПРП6, канал 3 — ПРП5, системный запрос добавляет ПРП12 |
| Канал 3 выставляет запрос, но ОС не отвечает | Свойство сборки Диспака: СВЯЗЬ7 обслуживает ДКС только на базовом канале 2 (ПРП6). Канал 3 проходит аппаратную цепочку, но ответов нет | Это не дефект моста (см. примечание в отчёте). Проверять многоканальность юнит-набором `dks_c_chans_test.sh`, где ОС-заглушка отвечает на оба канала |
| `got 0` в трассе Э-60, ответ ОС на CR зависает | Гонка по мосту: ОС пишет указатель кольца АБУФH раньше слота, и два КАДОПАМ-записа расходятся разными TCP-кадрами; drain читает устаревший слот 0 | Исправлено патчем 0020: слот 0 никогда не валиден, элемент откладывается на следующий тик. Убедиться, что сборка содержит исправление, и обновить бинарники |
| `bad magic` / `bridge: stale response dropped` / рост `BERR` | Рассинхрон потока кадров, поздний ответ после таймаута или несовпадение констант D6/D7 и опкодов | Сверить `BRIDGE_MAGIC_REQ/RSP`, коды 01–06 и смещения полей в `besm6_dks.c` и `pdp11_dks.c`; перезапустить оба процесса |
| Несовпадение констант `pdp11_dks.h` и `besm6_dks.c` | Заголовок объявлен «единственным источником», но физически продублирован в C-файле БЭСМ-6 | Сверить пары `A_BUFS/A_BUFH/A_FOSS/A_FOSH/RING_MASK/DOORBELL/DOORBELL_RING/ABONENT_OS/AREA_*` в обоих файлах после любой правки |
| Таймауты запросов, низкая отзывчивость | 1-мс опрос моста и буферизация TCP | В INI включены `DE INT-FLUSH ... 1` и `TCP_NODELAY`; `SET CLK SPEED=n` ускоряет модельное время (в приёмке 12.8 мс медианы при SPEED=8). Не увеличивайте таймауты теста раньше проверки журналов |
| Журнал пуст или обрывается | Трасса ушла в `SET DEBUG FILE`, который SIMH не fflush; либо процесс убит, не дождавшись выхода | Использовать `SET DEBUG -F LOG` и `logs/`, завершать симуляторы через Ctrl-E + QUIT и ждать выхода процесса |
| Ctrl-E не срабатывает, команды не вводятся | stdin — пайп, а не tty; SIMH опрашивает клавиатуру только при `isatty(0)` | Запускать симуляторы на pty (как в тестах через `pty.fork`) |
| Нет дисков / цикл на «УСТ.МД АРХИВА» | Не подключён том 2095 как `md05` | `attach -e md05 2095` в `dks_os_R.ini`; файл должен лежать в рабочем каталоге |

## 8. Что готово, а что предстоит

### 8.1 Уже готово в `simh` и зафиксировано в плане

- `BESM6/besm6_dks.c` — устройство DKS стороны БЭСМ-6: моделирование
  ОЗУ Э-60, команды 032/0132, режимы REMOTE/SHMEM, мост кадров,
  счётчики и debug-флаги.
- `besm6_cpu.c:1365–1371` — диспетчеризация 032/0132;
  `besm6_defs.h:538–541` — макросы `PRP_DKS_CHAN` и `PRP_DKS_ATTN`.
- `PDP11/pdp11_dks.c` и `pdp11_dks.h` — устройство Э-60: регистры
  CSR/RBUF/TSEL/TBUF/KADDR/KDATA/KCTL, FIFO, прерывания BR4, мост
  BRIDGE, обслуживание протокола.
- `PDP11/dks_fw.mac/.bin/.lst` — прошивка движка СВЯЗЬ7 для
  `ENGINE=HOST`; генерируется `PDP11/tests/gen_dks_fw.py`.
- Эталонные INI: `BESM6/OSZAGR/dks_os_R.ini`, `e60_R0.ini`,
  `e60_R1.ini`; SHMEM-варианты `dks_os_shm.ini`, `e60_shm0.ini`.
- Тесты `PDP11/tests/dks_*`: 63+ проверок, 0 FAIL. Приёмка с подлинной
  ОС Диспак: 9/9 локально и 11/11 через Э-60 по мосту, итого 20/20.
- Исправление гонки колец (патч 0020) и задержки (TCP_NODELAY, 1-мс опрос,
  `SET CLK SPEED=n`) включены в эталонные конфигурации.

### 8.2 Что предстоит для связки СМ-2 ↔ Э-60 (этап Q3a)

План `docs/PLAN-PERIFERIYA.md` ставит задачу Q3 «поднять мост DKS
БЭСМ-6 ↔ PDP-11, пропустить кадр 032/0132» — он **закрыт** этим
ранбуком. Следующий шаг Q3a — обмен через Э-60 между задачами `RCV`
и `SND` на СМ-2 и пакетом с CRC и двухфазным чтением.

Что ещё нужно сделать:

1. Соединить контроллер линии 2К СМ-2 (`HP2100/hp2100_sm2k.c`, регистр
   данных `SM2KD` и флаг `SM2KF`, настройка `SET SM2K SC=…`) с кадрами
   ДКС на Э-60. Сейчас связка идёт через хостовый драйвер, а не через
   прошивку Э-60 — это открытый GAP плана.
2. Реализовать на СМ-2 задачи `RCV`/`SND` по форматам из `re-mrv`:
   дескриптор блока из семи полей, таблица выдачи, пакет с кодом,
   числом параметров и контрольной суммой, двухфазное чтение
   (сначала сумма, затем исполнение; признак конца — `*50,IN E50`).
3. Добавить приёмочный тест `re-mrv/src/sm2_test/` как контрольную
   точку Q3a и добиться, чтобы он проверял и сторону Э-60, а не только
   БЭСМ-6 и формат пакетов.
4. Переходить к Q4–Q5 только после того, как задержка доставки
   команды через связку БЭСМ-6 ↔ Э-60 ↔ СМ-2 уложится в один шаг
   модельного времени.

Прошивку Э-60 переписывать не нужно: план прямо указывает
использовать готовую. Открытый вопрос — только точные битовые
раскладки кодов СМ-2 (в источнике их нет, кодировка `SM2_OP_*` — наша
декларация); до дизассемблирования `АД01`/модулей `LIBR1` диска 2248
совместимость с подлинной СМ-2 не гарантирована.
